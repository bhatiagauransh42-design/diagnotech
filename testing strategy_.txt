Diagnotech — Optimized Testing Strategy

1. Testing Objective

The objective of testing Diagnotech is not simply to verify that the website works.

The testing strategy must establish that:

«The system is functionally correct, the ML pipeline is scientifically valid, the API is secure, sensitive data is handled appropriately, explanations are consistent, and the deployed result matches the evaluated model.»

The testing strategy therefore covers six areas:

Functional Testing
      +
ML Validation
      +
API / Integration Testing
      +
Security & Privacy Testing
      +
UI/UX Testing
      +
Performance & Deployment Testing

For the SIH prototype, testing effort should be risk-based, not evenly distributed across every component.

---

2. Testing Philosophy

Diagnotech should follow four principles.

2.1 Test Critical Paths First

The most important path is:

Input
 ↓
Validation
 ↓
Preprocessing
 ↓
Model
 ↓
Prediction
 ↓
Explanation
 ↓
Response
 ↓
UI

If this path fails, the product fails.

---

2.2 Test the Model Separately From the UI

A beautiful UI cannot compensate for an invalid ML pipeline.

Therefore:

ML correctness ≠ UI correctness

Both must be tested independently.

---

2.3 Automate Repeatable Tests

Automate:

- API tests
- validation tests
- preprocessing tests
- model loading tests
- prediction-shape tests
- regression tests

Perform manually:

- visual UX checks
- accessibility review
- SIH demo rehearsal
- final end-to-end workflow

---

2.4 Never Use Test Data to Improve the Model

The test set must remain isolated.

Training
   ↓
Validation
   ↓
Model Selection
   ↓
FINAL TEST

No repeated tuning against the final test results.

---

3. Testing Pyramid

Use:

                    ┌───────────┐
                    │   E2E     │
                    │  Testing  │
                    └─────┬─────┘
                  ┌──────┴──────┐
                  │ Integration │
                  └──────┬──────┘
             ┌───────────┴───────────┐
             │      Unit Tests       │
             └───────────────────────┘

The majority of tests should be lower-level and automated.

Recommended target for the application layer:

- many unit tests
- moderate integration tests

10. ML Preprocessing Tests

This is a P0 category.

Test:

Feature order

Input features must reach the model in the expected order.

Scaling

Check that the same fitted scaler/preprocessor is used during inference.

Encoding

Check that category mappings remain consistent.

Missing-value handling

Verify deterministic behavior.

Output shape

Input:

1 sample

Expected:

1 prediction

---

11. Train/Inference Consistency Test

Create a regression test:

Known Input
    ↓
Saved Preprocessor
    ↓
Saved Model
    ↓
Expected Output

The deployed API must produce the same result as the offline inference pipeline for the same model version and input.

This is one of the highest-value tests in the project.

---

12. Model Loading Tests

At application startup:

Load Model
Load Preprocessor
Load Feature Schema
Load Metadata

Test that:

- files exist
- files are readable
- feature count matches
- model metadata matches
- model version is valid

If any P0 component fails, startup should fail clearly rather than silently deploying a broken model.

---

13. Prediction Tests

For every disease:

Known Input
 ↓
Prediction
 ↓
Probability
 ↓
Risk Category

Verify:

- prediction is valid
- probability lies within "[0, 1]"
- risk category is valid
- model version is returned
- disease name is correct

---

14. Prediction Regression Tests

Once a model is approved, create a small fixed set of inference cases.

Example:

Case A → expected class/probability range
Case B → expected class/probability range
Case C → expected class/probability range

After code changes, rerun them.

This helps detect accidental changes to preprocessing or model loading.

Don't require exact floating-point equality when tiny numerical differences are expected; use suitable tolerances.

---

15. ML Scientific Validation

This must be separated from normal software testing.

Validate:

Dataset

- class distribution
- duplicates
- missingness
- feature types

Evaluation

- stratified splitting
- cross-validation
- test isolation
- no leakage

Metrics

- accuracy
- precision
- recall
- specificity
- F1
- ROC-AUC
- PR-AUC where appropriate

---

16. Data Leakage Tests

Explicitly test for:

Duplicate leakage

Check whether duplicate/similar samples cross training/test boundaries.

Preprocessing leakage

Verify that scalers/imputers are fitted only on training data.

Feature leakage

Check for variables derived from the target or post-outcome information.

Test-set leakage

Confirm that final test data does not influence:

- feature selection
- hyperparameter tuning
- threshold selection

This is a release blocker if discovered.

---

17. Cross-Validation Stability

For each candidate model, capture:

Mean
Standard Deviation

Example:

ROC-AUC:
0.84 ± 0.03

Test for:

- unusually high variance
- unstable folds
- major differences between validation and final test

This helps prevent choosing a model because of one lucky split.

---

18. Class Imbalance Testing

Test model behavior when classes are imbalanced.

Inspect:

- recall
- specificity
- precision
- PR-AUC
- confusion matrix

Do not accept:

99% accuracy

without checking whether the model simply predicts the majority class.

---

19. Probability/Threshold Testing

Test several threshold values during model development.

For example:

0.30
0.40
0.50
0.60
0.70

Measure changes in:

- sensitivity
- specificity
- precision
- F1

The final threshold must be recorded as part of model metadata.

---

20. Calibration Testing

Where probability is presented to the user, test whether the output is reasonably calibrated.

Evaluate:

- calibration curve
- Brier score where appropriate

The UI should avoid presenting an unvalidated model score as if it were a clinically precise probability.

---

21. Explainability Testing

Test that every successful prediction produces an explanation.

Pipeline:

Prediction
 ↓
SHAP
 ↓
Feature Contributions

Verify:

- explanation is generated
- correct number of features returned
- feature names match model features
- ranking works
- values correspond to current input
- no unrelated user's data appears

---

22. Explanation Consistency Tests

For a fixed model/input:

same input
+
same model version

should produce consistent explanation output within expected numerical tolerance.

Also test:

change one input
       ↓
explanation changes appropriately

This is a sanity check, not proof of causality.

---

23. Explainability Regression Testing

Store a few known explanation examples.

After changing:

- SHAP version
- model
- preprocessing
- feature order

rerun them.

Any major change should be reviewed before release.

- expired token
- invalid token

Authorization

CORS

58. Quality Gates

The following should be release blockers:

P0 failures

- data leakage
- incorrect feature ordering
- broken preprocessing
- model cannot load
- incorrect prediction API
- probability outside valid range
- unauthorized data access
- exposed credentials
- major privacy violation
- critical security vulnerability
- broken Diabetes/CVD prediction workflow

---

59. P1 Failures

Should normally be fixed before release:

- broken analytics chart
- explanation formatting issue
- mobile layout issue
- non-critical API error
- moderate performance issue
- secondary browser issue

---

60. P2 Issues

Can be deferred for SIH:

- advanced dashboard polish
- screening-history edge cases
- rare browser issues
- non-critical animation bugs
- advanced admin features

70. Final Testing Principle

The most important test in Diagnotech is not:

«“Does the button work?”»

It is:

«“Does the exact data submitted by the user pass through the exact intended preprocessing pipeline into the exact approved model, produce a valid result, generate a consistent explanation, protect the user's data, and reach the UI without being misleading?”»

That single end-to-end principle should drive the entire testing strategy.

For the SIH MVP, the optimal approach is therefore P0-first: aggressively test the ML pipeline, leakage, prediction correctness, API validation, explainability, security/privacy, and two critical disease workflows, while keeping lower-value polish and advanced features behind those quality gates.

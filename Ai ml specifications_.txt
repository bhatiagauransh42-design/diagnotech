Diagnotech — AI/ML Technical Specifications

1. AI/ML System Overview

Diagnotech uses a disease-specific supervised learning architecture for early-risk screening of:

1. Diabetes
2. Cardiovascular Disease (CVD)

The AI subsystem has four major layers:

Clinical / Health Dataset
          ↓
Data Processing & Quality Control
          ↓
Feature Engineering & Selection
          ↓
Classical ML Models
          │
          ├───────────────┐
          │               │
          ▼               ▼
   Production Model   Quantum Benchmark
          │               │
          └───────┬───────┘
                  ▼
        Evaluation & Calibration
                  ↓
        Explainable AI Layer
                  ↓
       Prediction + Interpretation

The AI system must distinguish clearly between:

- prediction
- probability estimate
- model explanation
- medical interpretation

The first three are software outputs. The fourth should not be represented as a definitive medical diagnosis.

---

2. AI Objectives

The AI subsystem shall:

O1 — Predict

Estimate the probability of the target outcome from structured input data.

O2 — Classify

Convert model output into a documented screening category.

O3 — Explain

Identify the features that contributed most strongly to an individual prediction.

O4 — Compare

Evaluate multiple classical ML algorithms.

O5 — Benchmark Quantum ML

Compare a quantum-kernel hybrid model against classical baselines.

O6 — Measure Reliability

Evaluate models using clinically relevant classification metrics rather than accuracy alone.

O7 — Support Reproducibility

Track dataset versions, preprocessing, model versions, hyperparameters, and evaluation results.

10. Leakage Prevention

This is a mandatory AI requirement.

The following must never be fitted using the test set:

- imputation
- scaling
- encoding
- feature selection
- dimensionality reduction
- threshold optimization

Correct:

TRAIN
 ↓
Fit preprocessing
 ↓
Fit model

Then:

TEST
 ↓
Transform using fitted preprocessing
 ↓
Predict

12. Feature Engineering

Feature engineering should be driven by the dataset and documented.

Potential operations:

- derived ratios
- clinically meaningful transformations where justified
- logarithmic transformation for skewed variables
- interaction terms
- standardization

Do not introduce feature engineering solely to increase a benchmark number without a clear justification.

13. Feature Selection

Feature selection serves two objectives:

1. remove redundant/noisy features
2. simplify model interpretation and quantum processing

Potential methods:

Statistical

- correlation analysis
- mutual information
- univariate tests where appropriate

Model-based

- tree feature importance
- permutation importance
- recursive feature elimination

Feature selection must be performed inside the training/evaluation methodology to avoid leakage.

18. Class Imbalance Strategy

First inspect the class distribution.

If imbalance is significant, evaluate:

- class weighting
- stratified splits
- suitable resampling
- threshold tuning
- precision-recall performance

Potential techniques:

class_weight="balanced"

or resampling methods where appropriate.

Do not automatically apply SMOTE or other resampling methods without checking whether they improve the evaluation setup.

19. Evaluation Metrics

Each final candidate should report:

Accuracy

(TP + TN) / (TP + TN + FP + FN)

Precision

TP / (TP + FP)

Recall / Sensitivity

TP / (TP + FN)

Specificity

TN / (TN + FP)

F1 Score

2 × Precision × Recall
/
(Precision + Recall)

ROC-AUC

Area under the ROC curve.

PR-AUC

Useful especially when classes are imbalanced.

---

20. Screening-Oriented Evaluation

For this project, the AI dashboard must not rank models using accuracy alone.

Priority metrics should include:

Recall / Sensitivity
Specificity
ROC-AUC
Precision
F1
PR-AUC

The reason is that screening performance involves a trade-off between detecting potential positive cases and generating false alarms.

25. Threshold Management

Binary prediction depends on a decision threshold.

Default:

threshold = 0.50

may be used as a baseline, but the final threshold should be evaluated rather than assumed optimal.

Possible threshold analysis:

0.30
0.40
0.50
0.60
0.70

Compare:

- sensitivity
- specificity
- precision
- F1

The final operational threshold must be documented.

---

26. Calibration

Where probability interpretation matters, evaluate model calibration.

Potential tools:

- calibration curve
- Brier score
- calibration error

A model with high discrimination is not automatically well-calibrated.

If the deployed output is presented as a probability, calibration should be considered.

---

27. Model Selection Rule

The final model should be selected using a documented rule.

Example:

1. Remove models with poor validation stability.
2. Compare ROC-AUC and PR-AUC.
3. Compare recall and specificity.
4. Inspect calibration if probabilities are shown.
5. Consider interpretability and inference cost.
6. Evaluate on the untouched test set.
7. Register the final model.

The “best” model should not simply mean the model with the highest accuracy.

49. Bias and Fairness Analysis

Where the dataset contains suitable demographic variables, evaluate:

- sensitivity by subgroup
- specificity by subgroup
- precision by subgroup
- false-negative rate
- false-positive rate

     vs

50. Uncertainty and Limitations

The application should explicitly acknowledge:

- training dataset limitations
- sample size limitations
- distribution shift
- possible measurement errors
- missing variables
- model uncertainty
- lack of external clinical validation

The system should not claim general clinical validity from benchmark performance alone.

Do not include unnecessary identifiers in:

- model input
- training data
- logs
- experiment artifacts

For SIH demonstration, controlled or anonymized data is preferable.

66. Final AI/ML Principle

The AI architecture should be built around:

«Predict → Explain → Evaluate → Compare → Communicate Responsibly»

rather than:

«Train → Get Accuracy → Show Prediction»

That distinction is central to Diagnotech's technical credibility.
